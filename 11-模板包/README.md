# 一、导入书房的步骤

## 1.1 角色卡

**接口**：`POST /{AUTH_TOKEN}/api/oc/desk/import/card`

`角色卡/` 里的每个 `.json` 就是完整的请求体，只需要改一行 `project`：

```bash
# 1) 把 project 改成你自己的项目名，然后：
curl -X POST "http://<你的地址>/<AUTH_TOKEN>/api/oc/desk/import/card" \
     -H "Content-Type: application/json" \
     --data-binary @"角色卡/男主-高岭之花型.json"
```

批量导入（并顺手改 project）：

```bash
PROJ="我的项目"
for f in 角色卡/*.json; do
  jq --arg p "$PROJ" '.project = $p' "$f" \
  | curl -sS -X POST "http://<你的地址>/<AUTH_TOKEN>/api/oc/desk/import/card" \
         -H "Content-Type: application/json" --data-binary @-
  echo "  <- $f"
done
```

**只要卡本体，导进 SillyTavern 或别的前端时**：

```bash
jq '.card' "角色卡/男主-高岭之花型.json" > 高岭之花.card.json
```

### ⚠️ 导入后必做的两件事

① 补别名触发词。 导入后 `lore_keys` 只有角色名一个。想让别名、职务、代称也能触发这张卡的随身设定，导入后补一次：

```bash
curl -X PUT "http://<你的地址>/<AUTH_TOKEN>/api/oc/desk/lore/<返回的id>" \
     -H "Content-Type: application/json" \
     -d '{"keys":["裴叙白","裴老师","止方","修复师"]}'
```

② 把矫正指令粘进你自己的预设。 见 [1.4 的字段消费真相](#14-字段消费真相必读)。

## 1.2 世界书

**接口**：`POST /{AUTH_TOKEN}/api/oc/desk/import/worlds`

同样，每个 `.json` 就是完整请求体：

```bash
curl -X POST "http://<你的地址>/<AUTH_TOKEN>/api/oc/desk/import/worlds" \
     -H "Content-Type: application/json" \
     --data-binary @"世界书/女尊世界观基础包.json"
```

### 权力语言包与其他四个包不同

其余四包是设定包，管世界规则、称谓制度、体系约束。`权力语言包.json` 是语言习惯包，
数据直接来自 [13-语料挖掘](../13-语料挖掘/)（5,665 篇正文的频次统计），由
[`_脚本/build_langpack.py`](../_脚本/build_langpack.py) 生成，想改语料，重跑一遍脚本就行。

它的4条常驻是全部模板包里唯一「每一楼都该生效」的东西——语言习惯靠关键词触发就晚了，等词出现时那句话已经写完了。常驻总开销 **1,142 字**，是刻意压出来的。

| 常驻条目 | 约束的是 |
|---|---|
| 命令句：短到不能再短 | 命令句 2–6 字、不接解释、不用问号 |
| 顺从要写意志，不要只写身体 | 全语料前三名的顺从词全是生理性不自主反应，这是惯性不是标准 |
| 占有用陈述句，不用命名 | 「是我的」而非「我的狗」，后者是重口标记词 |
| 称谓换档就是情节 | 公开／私下／失控三档，掉档比升档有戏 |

其余7条按称谓类别女尊位分/宫廷/亲属/主奴/现代/师门军职和名场面关键词来触发，
内容是从正文里挑的真实用法，≤16字、至少跨5篇的类型套话，不是哪个作者自己的说法。

---

### ✅ 常驻条目：导入即生效，无需任何后续操作

> 本节曾写错，已实测更正。早先版本说「导入的条目 `trigger_mode` 恒为 `scan`，
> 所以标了常驻的条目并不会真常驻，需逐条 PUT 改成 presence」。那是把两个机制搞混了。

实测结论（2026-08，本地书房，训诫体系包 17 条）：导入后 `constant=true` 的 6 条全部正确落库并生效，包括三条安全框架条目。

两个机制的分工：这是书房世界书最容易搞错的一处。

| 机制 | 作用于 | 谁能用 | 导入时能不能设 |
|---|---|---|---|
| `constant`（常驻） | 不挑关键词，一直在 | `is_char=0` 的世界书条目 | ✅ 能，导进去就生效 |
| `trigger_mode: presence`（在场档） | 只看状态板上的在场名单 | `is_char=1` 的角色卡 | ❌ 导进去固定是 `scan`，得自己再改 |

也就是说：

- 世界书包用 `constant` 就行，所有【常驻】条目导进去直接能用，不用管别的。

- `presence` 档是给角色卡用的，专门解决「单字名角色被正文误触」的毛病。比如叫「寻」的角色会被「寻找」触发。世界书条目压根不看你 `trigger_mode` 设的啥。

角色卡才需要的两处后续操作，本包 36 张卡都受影响：

1. 关键词只填了名字。导入之后 `lore_keys` 永远都是 `["角色名"]`。想让别名、身份词也能触发，得手动补一下：
   ```bash
   curl -X PUT "http://localhost:8787/$TOK/api/oc/desk/lore/{entry_id}" \
     -H 'Content-Type: application/json' -d '{"keys":["裴叙白","裴老师","修复师"]}'
   ```
2. 单字名的角色建议开 presence 档，这个包里没有单字名角色，可以跳过：
   ```bash
   curl -X PUT ".../api/oc/desk/lore/{entry_id}" -d '{"is_char":true,"trigger_mode":"presence"}'
   ```

## 1.3 字段约束速查

### 角色卡 `data` 内被识别的字段

| 字段 | 必填 | 说明 |
|---|:--:|---|
| `name` | 是 | 没填或空着直接报 400 |
| `description` | | 实际用的时候会带上，没填就退回用 content |
| `personality` | | 实际用的时候会带上 |
| `scenario` | | 实际用的时候会带上 |
| `mes_example` | | 实际用的时候会带上 |
| `system_prompt` | | 存库时叫 `main_prompt`，用的时候不碰它 |
| `post_history_instructions` | | 存库，用的时候不碰它 |
| `first_mes` | | 只发给前端看，不存库 |
| `alternate_greetings`（数组） | | 只发给前端看，不存库 |
| `character_book` | | `{ "entries": [ ... ] }` |

其余一切字段一律忽略，并计入 warnings。（`avatar`、`tags`、`creator`、`character_version`、`creator_notes`、`extensions` 等都会进 warnings。本包的卡里一个都没写，导入时 warnings 应当是空的。）

### 世界书 `entries` 内被识别的字段

| 字段 | 说明 |
|---|---|
| `key` / `keys` | 关键词，数组 |
| `content` | 正文 |
| `comment` / `name` | 条目名 |
| `constant` | 常驻标记。导入即生效，无需后续操作，仅对 `is_char=0` 的世界书条目有效 |
| `enabled` / `disable` | 启用状态 |
| `position` | `1` / `after_char` / `after` → after。其余一切（含 `0`、`before_char`、缺失）→ before |

**不认的字段**：`keysecondary`、`selective`、`order`、`probability`、`depth`、`group`、`extensions`、`uid`、`role`。
本包的世界书只用被识别的六个字段，不会产生任何 warnings。

## 1.4 字段消费真相（必读）

这是使用本包时最容易踩的一个坑：

> 书房装配时实际消费的只有四个字段：`description`（缺时回退 content）、`personality`、`scenario`、`mes_example`。

于是：

卡里的 `system_prompt` 不会生效。
它在这张卡里就俩用处：① 你导进 SillyTavern 的时候能用上，② 当个备份，方便你复制到自己预设里。

卡里的 `post_history_instructions`（每楼自检）**也一样不生效**。
用途跟上面一样。

`first_mes` 和那两条 `alternate_greetings` 不会存进数据库。
它们只在导入的时候弹出来给你看一眼。
想留着就自己另存。
或者按 [开场白库](开场白/开场白库.md) 里那种用法，贴到新窗第一楼手动发出去。

本包的做法：每张卡都把该原型最容易跑偏的地方，直接压成一条提醒，塞在 `description` 末尾的「【扮演纪律】」那段里。那段是实打实会被用到的。
**你还需要做的**：去 [预设与正则](预设与正则/README.md) 里挑矫正指令，挑你用得上的，粘进你自己的预设里。

## 1.5 常见导入失败原因

| 现象 | 原因 | 怎么修 |
|---|---|---|
| 400，直接拒收 | `data.name` 没填或填了空字符串 | 把 `name` 补上。这是唯一必须填的 |
| 400 / 解析失败 | JSON 写坏了：多了逗号、用了中文引号、带注释、带 BOM | 先用 `python3 -m json.tool 文件.json` 验一遍。本包所有文件都验过了 |
| 导入成功但内容对不上 | body 层级写错——`data` 直接放顶层了 | 正确写法是 `{ "project": ..., "card": { "spec", "spec_version", "data": {...} } }` |
| warnings 一长串 | 卡里带了 `tags`/`creator`/`extensions`/`avatar` 这些它不认的字段 | 没影响，但可以用 `jq` 删掉。本包的卡不带这些 |
| 别名不触发 | 导入后 `lore_keys` 里只有角色名 | 用 `PUT /api/oc/desk/lore/{id}` 发 `{"keys":[...]}` |
| 角色卡只能靠名字触发 | 导入后 `lore_keys` 永远是 `["角色名"]` | 逐条 `PUT` 补 `keys`（见 1.2）。注意：这是角色卡的问题，世界书的 `constant` 不受影响 |
| `position` 没生效 | 只有 `1` / `after_char` / `after` 会被当成 after | 想放后面就写这三个值之一，其他值都会落到 before |
| 开场白导入后就没了 | `first_mes` / `alternate_greetings` 不存库 | 这是正常行为。自己另存，或者手动当第一楼发出去 |
| `system_prompt` 里的规则没生效 | 装配的时候没人去读它 | 自己粘进你的预设（见 1.4） |
| 世界书条目全部 disable | 用了 `disable` 而不是 `enabled`，值写反了 | 本包统一用 `"enabled": true`，不会有这问题 |

**自验命令**：导入前跑一遍，本包应当全部 OK。

```bash
for f in 角色卡/*.json 世界书/*.json; do
  python3 -m json.tool "$f" > /dev/null && echo "OK   $f" || echo "FAIL $f"
done
```

# 二、角色卡清单

> 每张卡的规格统一：`description` 写**三层状态**（人前／独处／破防下同一个动作的差异）＋【扮演纪律】；
> `personality` 写核心矛盾与顺从／主导的性质；`scenario` 交代权力落差从哪来；
> `mes_example` 2–3 组，示范「权力写在叙述层、礼貌写在对白层」；
> `system_prompt` 是针对该原型最易犯之病的**反 AI 味矫正指令**；
> `first_mes` ＋ 2 条 `alternate_greetings`；`character_book` 3–6 条随身设定（带 `⚠️主奴`／`⚠️非自愿`／`⚠️训诫`／`⚠️囚禁` 预警的卡必含一条常驻的「虚构与现实的区分」）。
> 所有涉性设定的角色均明确成年，年龄写在 description 第一行。

# 五、这一卷的设计原则

以下四条是本卷所有产物共用的技术底盘，改写模板时请一并保留。

## 5.1 把权力倒置写进设定，不写进人物的意愿

这是英文圈 monster romance 最值钱的一项技术，见 [01-总论/04-英文圈生态与出版市场](../01-总论/04-英文圈生态与出版市场.md) 第四节。男方比女方强太多，但生物设定让他根本伤不了她。权力倒挂直接写死在生理里，不靠 D/s 协议那套。女方不用抢权，也不用装强势。这个世界观天生就把权力塞她手里了。

本包的每一张卡都照此办理：

**检验法**：如果把「他愿意」三个字拿掉，权力关系还成立吗？不成立 → 你写的是人设声明，不是权力落差。

## 5.2 权力写在叙述层，礼貌写在对白层

主导方基本不说祈使句，台词永远是商量的口气。权力全藏在**叙述动词**里，比如「她吩咐道」。读者一眼收到俩信号：她挺客气，这其实是命令。

硬邦邦的命令一写出来就像反派，软绵绵的命令才是主导者该有的样子。这一包里每张卡的 `mes_example` 都在反复示范这个。

## 5.3 低位一方必须有反制手段

女攻的攻位，靠的不是「对方伤不了她」，而是「对方明明能伤她，却偏偏不碰她」。
每张卡的 `scenario` 里都有一条「反向落差（必须写）」。少了这条，你写的是单方面欺负人。

## 5.4 涉训诫／BDSM 的一切内容都附安全框架

按 [00-编纂规约/03-版权与内容红线](../00-编纂规约/03-版权与内容红线.md) 第 3.2 条：

- 现实 BDSM 的三套共识框架 SSC / RACK / PRICK，及其共同底盘：事前协商、可随时中止、事后照护。三者缺一，现实中就不是 BDSM 而是伤害。
- 虚构与现实的区分声明：小说里的非自愿、无安全词、无事后照护是幻想装置，不是现实实践指南。
- 涉及现实可复现的危险行为，包括呼吸限制、束缚、禁食禁水、用药、体温与灼伤类操作，本包只写叙事功能，不写操作细节。
- 你和 AI 之间的安全词是 OOC 指令：`[OOC: 停 / 换方向 / 降尺度 / 跳过这一场 / 补一段照护]`。它的优先级高于任何角色设定与剧情惯性。
