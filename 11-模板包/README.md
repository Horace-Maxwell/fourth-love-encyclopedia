# 一、导入书房的步骤

## 1.1 角色卡

**接口**：`POST /{AUTH_TOKEN}/api/oc/desk/import/card`

`角色卡/` 里每个 `.json` 都能直接当请求体发，要改的只有 `project` 这一行：

```bash
# 1) 把 project 改成你自己的项目名，然后：
curl -X POST "http://<你的地址>/<AUTH_TOKEN>/api/oc/desk/import/card" \
     -H "Content-Type: application/json" \
     --data-binary @"角色卡/男主-高岭之花型.json"
```

批量导入（并顺手改 project）：

```bash
PROJ="我的项目"
for f in 角色卡/*.json; do
  jq --arg p "$PROJ" '.project = $p' "$f" \
  | curl -sS -X POST "http://<你的地址>/<AUTH_TOKEN>/api/oc/desk/import/card" \
         -H "Content-Type: application/json" --data-binary @-
  echo "  <- $f"
done
```

**只想要卡本体，拿去导进 SillyTavern 或别的前端**：

```bash
jq '.card' "角色卡/男主-高岭之花型.json" > 高岭之花.card.json
```

### ⚠️ 导入后必做的两件事

① 补别名触发词。导入后的 `lore_keys` 里只有角色名。要让别名、职务、代称也能带出这张卡的随身设定，得在导入后补一次：

```bash
curl -X PUT "http://<你的地址>/<AUTH_TOKEN>/api/oc/desk/lore/<返回的id>" \
     -H "Content-Type: application/json" \
     -d '{"keys":["裴叙白","裴老师","止方","修复师"]}'
```

② 把矫正指令粘到你自己的预设里，原因见 [1.4 的字段消费真相](#14-字段消费真相必读)。

## 1.2 世界书

**接口**：`POST /{AUTH_TOKEN}/api/oc/desk/import/worlds`

同样，每个 `.json` 就是完整请求体：

```bash
curl -X POST "http://<你的地址>/<AUTH_TOKEN>/api/oc/desk/import/worlds" \
     -H "Content-Type: application/json" \
     --data-binary @"世界书/女尊世界观基础包.json"
```

### 权力语言包与其他四个包不同

设定包共五个。四个管世界规则、称谓制度和体系约束，另一个管语言习惯，就是 `权力语言包.json`。
它是 [`_脚本/build_langpack.py`](../_脚本/build_langpack.py) 跑出来的，数据取自 [13-语料挖掘](../13-语料挖掘/)（5,665 篇正文的频次统计）。
语料要改的话，把脚本重跑一遍。

全部模板包里常驻的只有这4条，「每一楼都该生效」的只有它们。语言习惯等关键词来触发就晚了，词一出现，那句话已经写完了。所以要常驻，而常驻的总开销 **1,142 字** 是特意压出来的。

| 常驻条目 | 约束的是 |
|---|---|
| 命令句：短到不能再短 | 2–6 字一句，后面不跟解释，不用问号 |
| 顺从要写意志，不要只写身体 | 全语料排前三的顺从词，都是身体不由自主的反应，这是惯性 |
| 占有用陈述句，不用命名 | 写「是我的」，别写「我的狗」，「我的狗」是重口标记词 |
| 称谓换档就是情节 | 分公开、私下、失控三档，掉档比升档更有戏 |

另外7条按关键词触发：称谓类有女尊位分/宫廷/亲属/主奴/现代/师门军职，还有名场面。
内容是从正文里挑的真实用法，每条≤16字，都是至少跨5篇的类型套话。

---

### ✅ 常驻条目：导入即生效，无需任何后续操作

> 本节以前写错，已按实测改正。早先版本说「导入的条目 `trigger_mode` 恒为 `scan`，
> 所以标了常驻的条目并不会真常驻，需逐条 PUT 改成 presence」。这话把两个机制混为一谈了。

实测结论（2026-08，本地书房，训诫体系包 17 条）：导入后 `constant=true` 的 6 条全部正确落库并生效，包括三条安全框架条目。

用书房世界书，人最常搞混的就是这两个机制各管什么。

| 机制 | 作用于 | 谁能用 | 导入时能不能设 |
|---|---|---|---|
| `constant`（常驻） | 不挑关键词，一直在 | `is_char=0` 的世界书条目 | ✅ 能，导进去就生效 |
| `trigger_mode: presence`（在场档） | 只看状态板上的在场名单 | `is_char=1` 的角色卡 | ❌ 导进去固定是 `scan`，得自己再改 |

也就是说：

- 世界书包用 `constant` 就行，标了【常驻】的条目导进去就生效，别的不用管。

- `presence` 档只给角色卡用，治的是「单字名角色被正文误触」，比如名叫「寻」的角色，正文一出现「寻找」就被带出来。世界书条目根本不读 `trigger_mode`，你设成什么都一样。

下面两处后续操作只跟角色卡有关，本包 36 张卡都涉及：

1. 导入时关键词只填名字，所以导进来的 `lore_keys` 一律是 `["角色名"]`。别名、身份词要能触发，就得手动补：
   ```bash
   curl -X PUT "http://localhost:8787/$TOK/api/oc/desk/lore/{entry_id}" \
     -H 'Content-Type: application/json' -d '{"keys":["裴叙白","裴老师","修复师"]}'
   ```
2. 角色名只有一个字的，建议开 presence 档。本包没有这样的角色，这一步可以跳过：
   ```bash
   curl -X PUT ".../api/oc/desk/lore/{entry_id}" -d '{"is_char":true,"trigger_mode":"presence"}'
   ```

## 1.3 字段约束速查

### 角色卡 `data` 内被识别的字段

| 字段 | 必填 | 说明 |
|---|:--:|---|
| `name` | 是 | 没填或空着直接报 400 |
| `description` | | 用的时候会读进去，空着就拿 content 顶上 |
| `personality` | | 实际用的时候会带上 |
| `scenario` | | 实际用的时候会带上 |
| `mes_example` | | 实际用的时候会带上 |
| `system_prompt` | | 存库时叫 `main_prompt`，用的时候不碰它 |
| `post_history_instructions` | | 存库，用的时候不碰它 |
| `first_mes` | | 只发给前端看，不存库 |
| `alternate_greetings`（数组） | | 只发给前端看，不存库 |
| `character_book` | | `{ "entries": [ ... ] }` |

别的字段全都不读，会记进 warnings，像 `avatar`、`tags`、`creator`、`character_version`、`creator_notes`、`extensions` 这些。本包的卡一个也没写，所以导入时 warnings 应该是空的。

### 世界书 `entries` 内被识别的字段

| 字段 | 说明 |
|---|---|
| `key` / `keys` | 关键词，数组 |
| `content` | 正文 |
| `comment` / `name` | 条目名 |
| `constant` | 常驻标记，导进去就生效，不用再做什么。只管 `is_char=0` 的世界书条目 |
| `enabled` / `disable` | 启用状态 |
| `position` | `1` / `after_char` / `after` → after。其余一切（含 `0`、`before_char`、缺失）→ before |

**不认的字段**：`keysecondary`、`selective`、`order`、`probability`、`depth`、`group`、`extensions`、`uid`、`role`。
本包世界书只用它认得的六个字段，导入不会出任何 warnings。

## 1.4 字段消费真相（必读）

用本包时，踩坑最多的就是这儿。

> 书房装配时真正读进去的字段只有四个：`description`（空着就用 content）、`personality`、`scenario`、`mes_example`。

于是：

卡里的 `system_prompt` 装配时不会生效。
留着它有两个用处：① 导进 SillyTavern 时能用，② 当备份，方便你复制进自己的预设。

卡里的 `post_history_instructions`（每楼自检）**同样不生效**，
留着它的用处和上一条一样。

`first_mes` 和两条 `alternate_greetings` 不进数据库，
只在导入时弹出来让你看一眼。
想留就自己存一份，
或者照 [开场白库](开场白/开场白库.md) 的用法，开新窗时贴进第一楼手动发。

每张卡 `description` 的末尾有一段「【扮演纪律】」，写的是这个原型最容易跑偏的地方，压成一条提醒放在那里，装配时真会读到。
剩下要你自己做的，是去 [预设与正则](预设与正则/README.md) 里挑用得上的矫正指令，**粘进你自己的预设**。

## 1.5 常见导入失败原因

| 现象 | 原因 | 怎么修 |
|---|---|---|
| 400，直接拒收 | `data.name` 没填，或者是空字符串 | 补上 `name`，必填的字段只有它 |
| 400 / 解析失败 | JSON 格式坏了，比如多逗号、中文引号、注释、BOM | 先跑 `python3 -m json.tool 文件.json` 检查。本包的文件全都检查过 |
| 导入成功但内容对不上 | body 层级错了，`data` 被放到了顶层 | 应该写成 `{ "project": ..., "card": { "spec", "spec_version", "data": {...} } }` |
| warnings 一长串 | 卡里有 `tags`/`creator`/`extensions`/`avatar` 这类书房不认的字段 | 不碍事，想清掉可以用 `jq` 删。本包的卡里没有这些 |
| 别名不触发 | 导入后的 `lore_keys` 只有角色名一项 | 发 `PUT /api/oc/desk/lore/{id}`，body 写 `{"keys":[...]}` |
| 角色卡只能靠名字触发 | 导入后的 `lore_keys` 一律是 `["角色名"]` | 一条条 `PUT` 补上 `keys`（见 1.2）。只有角色卡会这样，世界书的 `constant` 照常生效 |
| `position` 没生效 | 被当成 after 的只有 `1` / `after_char` / `after` | 要放后面就从这三个里挑，写别的值一律算 before |
| 开场白导入后就没了 | `first_mes` / `alternate_greetings` 本来就不进数据库 | 正常现象。自己存一份，或者手动贴成第一楼发出去 |
| `system_prompt` 里的规则没生效 | 装配时根本不读这个字段 | 把它粘进你自己的预设（见 1.4） |
| 世界书条目全部 disable | 写成了 `disable` 字段，该用 `enabled`，值也就反了 | 本包一律写 `"enabled": true`，碰不到这个问题 |

**自验命令**：导入前跑一遍，本包的文件应全部 OK。

```bash
for f in 角色卡/*.json 世界书/*.json; do
  python3 -m json.tool "$f" > /dev/null && echo "OK   $f" || echo "FAIL $f"
done
```

# 二、角色卡清单

> 所有卡写法统一：`description` 写**三层状态**（同一个动作在人前、独处、破防时的差别），加【扮演纪律】。
> `personality` 写核心矛盾，以及顺从或主导是哪一种。`scenario` 写权力落差从哪来。
> `mes_example` 给 2–3 组，演示「权力写在叙述层、礼貌写在对白层」。
> `system_prompt` 放**反 AI 味矫正指令**，专挑这个原型最常犯的毛病来写。
> `first_mes` 加 2 条 `alternate_greetings`，`character_book` 放 3–6 条随身设定。标了 `⚠️主奴`／`⚠️非自愿`／`⚠️训诫`／`⚠️囚禁` 预警的卡，一定有一条常驻的「虚构与现实的区分」。
> 凡是有涉性设定的角色，都写明了已成年，年龄就在 description 的第一行。

# 五、这一卷的设计原则

下面四条，本卷每件东西都用到了。改模板时请把它们一起留着。

## 5.1 把权力倒置写进设定，不写进人物的意愿

英文圈 monster romance 有一项技术：把权力倒挂直接写死在生理设定里，详见 [01-总论/04-英文圈生态与出版市场](../01-总论/04-英文圈生态与出版市场.md) 第四节。男方再强，生物设定决定了他根本伤不了她。这里用不着 D/s 协议那一套，权力生来就在女方手里，她用不着抢，也用不着装。「女方怎么压得住男方」这个问题，世界观本身就解决了。

**检验法**：拿掉「他愿意」这三个字，权力关系还站得住吗？站不住，那写出来的只是人设声明。

## 5.2 权力写在叙述层，礼貌写在对白层

主导的一方很少用祈使句，说出口的永远是商量的语气。权力都在**叙述动词**里，比如「她吩咐道」。读者同时读到两层意思：她很客气，而这是一道命令。

命令写得硬邦邦，人物就像反派。本包每张卡的 `mes_example` 都在一遍遍示范这一点。

## 5.3 低位一方必须有反制手段

女攻能站在攻位上，靠的是「对方明明能伤她，却偏偏不碰她」。
所以每张卡的 `scenario` 都有一条「反向落差（必须写）」，缺了它，故事就成了单方面欺负人。

## 5.4 涉训诫／BDSM 的一切内容都附安全框架

按 [00-编纂规约/03-版权与内容红线](../00-编纂规约/03-版权与内容红线.md) 第 3.2 条：

- 现实 BDSM 的三套共识框架 SSC / RACK / PRICK，及其共同底盘：事前协商、可随时中止、事后照护。三者缺一，现实中就不是 BDSM 而是伤害。
- 虚构与现实的区分声明：小说里的非自愿、无安全词、无事后照护是幻想装置，不是现实实践指南。
- 涉及现实可复现的危险行为，包括呼吸限制、束缚、禁食禁水、用药、体温与灼伤类操作，本包只写叙事功能，不写操作细节。
- 你和 AI 之间的安全词是 OOC 指令：`[OOC: 停 / 换方向 / 降尺度 / 跳过这一场 / 补一段照护]`。它的优先级高于任何角色设定与剧情惯性。

# 七、编纂说明

- **分级**：本卷整体标为 `M`。角色卡和世界书只写关系结构和技法，没有器官级的描写。带 `⚠️主奴` `⚠️非自愿(制度性)` `⚠️囚禁(倾向)` `⚠️np` `△虐身` `△虐心` `△上下级` 这些预警的卡，文件第一行已经标出来了。
- **成年声明**：凡有涉性设定的角色，都写明已成年，年龄在 `description` 的第一行。
- **扮演方向**：「我扮女主／AI 扮男主」19 张，「我扮男主／AI 扮女主」17 张。四爱男和四爱女本包都照顾到了，两个方向卡数接近，质量对等。
- **实证来源**：原型类型学、结构手法和语感规律，来自对四部作品的精读，即《墨氏家规》《失忆后你和霸总破镜重圆了》《女Alpha掉马后果很严重》《风起云涌》。亚型覆盖的依据是 [10-藏书索引-公开/语料统计](../10-藏书索引-公开/语料统计.md)，权力编码的思路来自 [01-总论/04](../01-总论/04-英文圈生态与出版市场.md)。
- **全部内容原创。** 角色的姓名、身世、设定、台词、开场白都是本卷自己写的，没有从藏书里抄任何表达。拿来提炼的只有模式：原型类型学、结构手法、语感规律、场景骨架。按 [00-编纂规约/03-版权与内容红线](../00-编纂规约/03-版权与内容红线.md) 1.1 条，这些属于可以提炼的范围。
- **去 AI 化**：36 张卡的 `description` 里没有元评论，找不到「这张卡」「这一格」「读者会」这类谈卡本身的句子。这种写作指导只放在 `system_prompt` 和随卡世界书里，那两处本来就是写给使用者看的。所有字段合起来，加粗是 1.0 处/千字，低于 [00-编纂规约/05-去AI化写作铁律](../00-编纂规约/05-去AI化写作铁律.md) 的 10 处/千字阈值。
- 41 个 JSON 文件（36 张角色卡 ＋ 5 个世界书包）全都过了 `python3 -m json.tool` 的检查，用的也都是书房认得的字段。36 张角色卡一张张导进本地书房实测过：**36/36 success，warnings 全部为 0**，随卡世界书条目 160 条都正确落库。本地开发环境没挂 `[[vectorize]]` 和 `[ai]` 绑定，所以回包里的 `vector_ok` 一直是 `false`。照 `importCharacterCard` 的约定，向量化只是 best-effort，D1 落库和导入成功都不受它影响。
