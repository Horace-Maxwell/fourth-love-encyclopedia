# 工作流程

`G` ｜ 无预警 ｜ `元文档`
来源：本库建设过程中实际踩过的错误

> 提示：本篇是操作规程。写条目的规矩在 [02-条目写作模板](02-条目写作模板.md)，文风在 [05-去AI化写作铁律](05-去AI化写作铁律.md)。

## 一、统一入口

不要记散命令。所有流程走这一个文件：

```bash
python3 _脚本/run.py doctor     # 体检：报状态与待办，不改文件
python3 _脚本/run.py check      # 交付前自查，写完任何内容都跑
python3 _脚本/run.py rebuild    # 重建导出，改了主库正文之后
python3 _脚本/run.py mine       # 重跑语料统计，加了新素材，约 50 分钟
python3 _脚本/run.py publish    # 发布前全套
```

顺序被写进了代码。手工按记忆执行时漏过一步，出来的结果就是错的，不只是难看（见第四节）。

## 二、四种场景

| 场景 | 跑什么 | 说明 |
|---|---|---|
| 写了一条新条目 / 改了正文 | `run.py check` → 改到通过 → `run.py rebuild` | check 不通过别提交 |
| 加了新藏书 | `export GB_CORPUS=...` → `run.py mine` → `run.py rebuild` | mine 约 50 分钟 |
| 新写了角色卡 / 情景卡 | `run.py check`（K 项查卡）→ 实测导入 | 情景卡改 `build_scene_cards.py` 的 `CARDS` 表后重跑，别直接改 JSON |
| 新加了桥段 | `run.py check`（L 项查十一格与双向覆盖） | 缺格会逐条报出来 |
| 准备推送 | `run.py publish` | 含 preflight 风险扫描 |

## 三、三道自动检查

| 脚本 | 查什么 | 不通过的后果 |
|---|---|---|
| `check_compliance.py` | A 三行头 · B 分级就高不就低 · C 安全框架 · D 写崩标题 · E 来源声明 · F 链接 · G 双链 · H 引用配额 · I 成句引用出处 · J 去 AI 化铁律 · K 角色卡与情景卡 · L 桥段栏目与双向覆盖 · M 渲染种子 · N 文风分布层 · O 有序列表编号 | 内容不合规约 |
| `sync_index.py` | 全库数字与 `aggregate_corpus.CANON` 一致，派生统计漂移，HTML 篇数 / 术语总条数 / 卡片张数 | 数字自相矛盾 |
| `preflight.py` | 本机路径 · 密钥 · 藏书清单 · 隐私 · 必备文件 | 发布出事 |

后两项是后加的，加的理由都是同一类：同一个数在三到四处手写，加一卷就漏改一处。

| 检查项 | 对应的实际错误 |
|---|---|
| L 桥段栏目 | 90 条里有 43 条漏了「节拍链」这一格，人眼数不出来 |
| L 双向覆盖 | 「双向写法」两栏只填一边等于没填，而本库同时服务两边读者 |
| HTML 篇数 | 加了 14 卷之后，README / INDEX / 12 卷 / 06-发布风险评估 四处仍写着旧的 69 |
| 术语总条数 | 声明「311 条」而速查表实际 315 行，差了 4 且没人发现 |
| O 有序列表编号 | 批量重排把红线第二节打乱成 5→4→2→1→3，参考文献第 10 条被甩到末尾，全库 12 处，人眼扫不出来 |

HTML 篇数的做法值得记：让 `build_exports` 在文件首行写一个机读标记 `<!--gb-html-docs:N-->`，
`sync_index` 读它来核。把真值放在产物里，比让人记住去改四个地方可靠。

三个都设计成**可复跑、报具体位置**。报出来的每一条，都是真实踩过的错，不是预防性洁癖。

## 四、顺序为什么不能乱

以下每一条都真实发生过。跑完了，没报错。结果却是错的。这类错误不会自己暴露。

| 顺序 | 违反后果 | 实测 |
|---|---|---|
| `fix_mojibake` 必须在 `aggregate_corpus` 之前 | 文件名乱码没还原就聚合，带 GB 标记的作品被误判成「非本类型」剔除 | 漏掉 68 篇，「女攻」标签少算 1,766 次 |
| `probe_v2` 必须在 `organize_corpus` 之前 | 整理视图是硬链接目录，被探针当成源文件扫进去 | 原始文件数从 13,285 虚增到 16,425 |
| 改完主库必须 `rebuild` | 导出产物留着旧数字与旧内容 | HTML 里出现已被推翻的结论 |
| `mine` 之后必须 `rebuild` | 13 卷更新了但导出没跟上 | 同上 |
| `mine_vignette` 必须在 `render_vignette` 之前 | 渲染器读的是挖掘产出的 JSON，顺序颠倒会渲染上一轮的数据 | 14 卷频次与 13-07 对不上 |

`run.py` 已经把顺序固化。照它跑就行。

## 四之二、挖掘类脚本的三条方法论

这三条来自桥段层挖掘，但适用于所有新增的挖掘脚本。

### 4.1 单模式命中在「结构层」必然失效

mine_text` 的八类元素靠单模式命中就够，因为它们是「点」：人名、命令句、道具。
桥段是「链」，同样的做法在这一层会全是噪声：

| 模式 | 本意 | 实际命中 |
|---|---|---|
| 「热了一次」 | 等门热菜 | 教主等下属 |
| 「等到睡着」 | 等到睡着 | 修真炉鼎戏 |

改成共现判据之后结果才成立：**情境族 ≥2 且反应族 ≥1 落在同一个 2,500 字窗口内**。

分情境族与反应族两类是必需的。第一版用「任意 3 族共现」，命中率 99%，
组合榜前十全是「哭＋抱＋撒娇」，等于没测。反应族在任何言情里都高频，它们不定义场景。

### 4.2 不预设目录，让聚类反过来命名

节拍族定义的是「做饭／等待／哭」这种原子动作，不是「等门热菜」这种桥段名。
桥段名由共现组合的聚类结果反过来命名。

先写目录再去语料里找确认，只会挖到自己写下的东西。实测：按预设触发词去找，
回来的是邻近桥段：生病照顾＋投喂、瞒病被拆穿、临终守候，不是预设的那一个。

### 4.3 抽不动就降级成验真器，别硬抽

开放域名词抽取失败过两版，失败方式都值得记：

| 版本 | 做法 | 抽出来的是 |
|---|---|---|
| v1 | 「把／放／拿／递 + X」 | 趋向补语（放下来→「下来」） |
| v2 | 量词锚定（一碗汤、那把伞） | 词性对了，但量词也搭配抽象状态（一片空白），300 部里只活下来 9 个词 |
| v3 | 受控词表实测 | 可用 |

v3 把脚本从**发现器**降级成**验真器**：词表由编者出，脚本只回答「这个物件在多少部
不同作品的桥段窗口里出现过」，外加提升度，即本场出现率 ÷ 一般桥段出现率。
代价是词表外的物件测不到，换来的是每个数字都可复现。

真正的特征物件，得等提升度算完才浮出来：生病场的体温计 1.8×、归家场的玄关 1.9×、守夜场的冰袋 3.6×。
这一步绕不开——门、车、药、手机在每场戏里都排前列，它们只是背景，不是特征。

## 五、与模型协作的纪律

批量重写交给子代理、或者交给外部模型时，下面这些必须写进任务说明。
每一条都对应一次实际事故。5.1–5.5 来自早期的子代理轮次，5.6 起来自 2026-08
那八轮外部模型批量改写。

### 5.1 不许用「删标记」代替「改结构」

去 AI 化的正确做法是把散文改成表格，加粗自然下降。只删 `**` 号可以让指标达标。**什么都没改善**。

拿两个数一起看：

| 现象 | 判断 |
|---|---|
| 表格数没涨、汉字数没涨 | 一定是假的 |
| 表格数涨了、汉字数涨了 5–13% | 真的改了结构 |

实测：某份精读笔记第一版「表 12→12、汉字 −0.1%」，退回重做后是「表 12→29、汉字 +6.4%」。

### 5.2 不许为指标改引文

外部引文，即作品原文、社群发言、平台规则、学术文献，**一字不动**。如果它触发了文风指标，就在文件里注明例外。

优先级：**内容红线 > 分级与预警 > 去 AI 化铁律**。

区分见 [05-去AI化写作铁律](05-去AI化写作铁律.md)「外部引文与自引不是一回事」。

### 5.3 机械批处理必须先说清豁免

正则批量处理会误伤结构性标记。已经踩过的：

| 批处理 | 误伤了什么 |
|---|---|
| 表格单元格一律去粗 | 精读笔记信息框的字段名，那是分级判定的唯一依据 |
| 整句加粗一律去掉 | 预警标签，那是元数据不是强调 |

### 5.4 任务说明里要给可测目标与核验方法

不要只说「去 AI 化」。要给：当前值、目标值、用哪个脚本测、哪些内容不许动、改完怎么自证没删信息，即汉字数对比、链接比对、引文比对。

### 5.5 代理的报告要复核，不要照单全收

本轮子代理报告里出现过的不实之处：

- 声称「已把第九个取值填入 0.2 表」，实际只写进了原型表，正表没加
- 声称「全部 30 张卡零元评论」，实际 18 张在 `system_prompt` 与随卡世界书里有
- 声称「安全框架完整」，实际 5 张带高风险预警的卡缺 SSC/RACK/PRICK

凡是可测的断言都要**自己跑一遍**。这也是把检查做成脚本的理由，复核成本必须低到愿意每次都做。

### 5.6 分工：模型改，判据判

让模型拆一个具体的括号、换一个行话、把一句翻译腔拉直，它做得干脆利落。
让它下「这段像不像 AI 写的」这种整体判断，实测跟抛硬币差不多
（数据见 [05-去AI化写作铁律](05-去AI化写作铁律.md) 第六节）。

所以分工定死：**具体的改交给模型，判断交给可复算的判据。**
判据要有分布、有分位数、能拿已知答案的样本验。

### 5.7 闸门要反着写

批量作业必须配自动闸门，任何一条不过就退回原文。宁可不改，不能改坏。
闸门分两种，方向反了就等于没有：

| 写法 | 效果 |
|---|---|
| 「括号不许变多」 | 模型挑软柿子捏，密度只从 7.4 掉到 6.1 |
| 「指定的这个括号必须消失」 | 同一批文本，密度掉到 3.8 |

**判据松一格，结果就差一截。** 要它做到什么，闸门就写成「必须做到」，
不要写成「不许更糟」。

标准闸门清单（批量改文本时至少这些）：

- 数字：阿拉伯数字和中文数字都要。重排最容易把「第三拍」写成「后面那拍」，
  只查阿拉伯数字的闸门看不见这种丢失
- markdown 链接的**地址**、竖线数、加粗数、行数、`<!--` 机读标记数
- 「」里超过十来个字的整句（引文，红线 1.3）
- 安全框架的 SSC/RACK/PRICK 字面
- 篇幅区间。缩太狠是删内容，涨太多是编内容
- 引号体例：库里全用「」，模型爱换成 “”

### 5.8 三类反向验证

正向问「改好了吗」得不到有用的答案。要问反向的、具体到可以回答的问题：

| 问题 | 抓什么 | 为什么反着问 |
|---|---|---|
| 新版里哪句话是旧版没有的 | 编造 | 编造是具体的、看得见的；问「漏了什么」要通读比对，模型做不好 |
| 这段里有没有指代不明的地方 | 重排打断的指代 | 「这五样东西」被挪到「五样东西」还没出现的位置，机械闸门全绿，话读不通 |
| 意思变了没有 | 语义漂移 | 二选一的问题比开放问题稳 |

### 5.9 做新判据之前先校准

拿两组已知答案的样本喂进去，看它分不分得开。分不开就别用。

第一版 AI 检测器把送检的 96 段**全部**判成有病，原因是三个评审里有一个的问法是
「下面这段是 AI 写的，找出最露馅的一句」，那是一张永远投阳性的票。
一个把什么都判成阳性的检测器，测不出任何东西。

判据每收窄一格，也要回头再验一次它还报不报得出真毛病。
「让库通过」会在某一步悄悄替换掉「把库改好」，而且换得无声无息。

### 5.10 改写换不掉骨架，重写才行；但重写不能不给原文

AI 味有一层住在骨架上：先说哪件事、怎么起句、用什么收尾。改词改标点动不了它。

试过「抽要点 → 不给原文让它重写」，实测失败且危险：抽要点时丢整句内容，
重写时凭空编（编出库里根本没有的圈内说法），篇幅涨到 2.74 倍。
**看不见原文，模型就会编。**

可行的做法是给它看原文，把「换骨架」写成硬要求：换开头、换顺序、换收尾，事实一条不许增删。再配 5.7 的闸门和 5.8 的反向验证。
另加一道**差异闸**：首句必须不同、整体相似度低于 0.72，否则它只换几个词交差。

已经换过骨架的段落不要再炒第二遍，那是传话游戏。
真要跑第二轮，先按「跟上一轮的备份逐段比对」筛出没换成的那些，只打它们。

### 5.11 批量改写之前，先认清哪些字是机器在读的

这些是接口不是文风，改一个近义词检查器就报错，而报出来的错和你改的地方对不上号：

三行头、分级行 `` `T` ｜ ``、`**骨架**｜`、`#### 六栏目` 的字面、
判据条的豁免标记 `<!-- gb-nonscene -->`、安全声明里的
「幻想装置／不是现实指南／SSC/RACK/PRICK」、角色卡 description 开头的「扮演方向：」声明行。

改写脚本要把它们整块跳过。已经踩过的：
「幻想装置」被写成「幻想道具」，C 项当场报缺声明；
「不是一场戏」被改成「这条不算具体场景」，L 项当场报缺栏目；
30 张角色卡的「扮演方向：」被冲掉，K 项全线飘红。

### 5.12 有序列表不是散文

「重排句序」这条指令会把有序列表也重排掉：条目换位置，编号跟着条目走。
数字、链接、篇幅、markdown 全对，闸门全绿，**列表的顺序不在任何一道闸里**。
红线第二节曾经变成 5→4→2→1→3，参考文献的第 10 条被甩到第 15 条后面。
全库当时有 12 处，人眼扫不出来。

现在是检查器的 **O 项**。批量改写时也应当把有序列表整段跳过。

## 六、发布

| 步骤 | 命令 / 说明 |
|---|---|
| 1. 全套检查 | `python3 _脚本/run.py publish` |
| 2. 确认入库清单 | `git status --porcelain`，核对没有 `10-藏书索引/`、`*.jsonl`、挖掘 JSON |
| 3. 提交 | 提交信息写清规模与发布边界 |
| 4. 推送 | 首次 `git remote add origin <url> && git push -u origin main` |

发布边界的完整论证见 [06-发布风险评估](06-发布风险评估.md)。要点：**不发藏书逐条清单，只发聚合统计**。

## 七、加新素材的完整一轮

```bash
export GB_CORPUS=/path/to/your/corpus
python3 _脚本/run.py mine      # 约 50 分钟
python3 _脚本/run.py rebuild
python3 _脚本/run.py check
```

新素材极可能全是重复。一次「新增 4,025 篇」经 MD5 校验，100% 是已有内容的副本。`check_new.py` 已在 `mine` 的第一步，不会白跑后面的统计。
