# 工作流程

`G` ｜ 无预警 ｜ `元文档`
来源：本库建设过程中实际踩过的错误

> 提示：这里讲的是操作步骤。条目怎么写看 [02-条目写作模板](02-条目写作模板.md)，文风看 [05-去AI化写作铁律](05-去AI化写作铁律.md)。

## 一、统一入口

别记零散命令，所有流程都走这一个文件：

```bash
python3 _脚本/run.py doctor     # 体检：报状态与待办，不改文件
python3 _脚本/run.py check      # 交付前自查，写完任何内容都跑
python3 _脚本/run.py rebuild    # 重建导出，改了主库正文之后
python3 _脚本/run.py mine       # 重跑语料统计，加了新素材，约 50 分钟
python3 _脚本/run.py publish    # 发布前全套
```

顺序已经写死在代码里。凭记忆手动跑，漏一步，结果就是错的（见第四节）。难看还算小事。

## 二、四种场景

| 场景 | 跑什么 | 说明 |
|---|---|---|
| 写了一条新条目 / 改了正文 | `run.py check` → 改到通过 → `run.py rebuild` | check 不通过别提交 |
| 加了新藏书 | `export GB_CORPUS=...` → `run.py mine` → `run.py rebuild` | mine 约 50 分钟 |
| 新写了角色卡 / 情景卡 | `run.py check`（K 项查卡）→ 实测导入 | 情景卡要改 `build_scene_cards.py` 里的 `CARDS` 表再重跑，不要直接动 JSON |
| 新加了桥段 | `run.py check`（L 项查十一格与双向覆盖） | 缺格会逐条报出来 |
| 准备推送 | `run.py publish` | 含 preflight 风险扫描 |

## 三、三道自动检查

| 脚本 | 查什么 | 不通过的后果 |
|---|---|---|
| `check_compliance.py` | A 三行头 · B 分级就高不就低 · C 安全框架 · D 写崩标题 · E 来源声明 · F 链接 · G 双链 · H 引用配额 · I 成句引用出处 · J 去 AI 化铁律 · K 角色卡与情景卡 · L 桥段栏目与双向覆盖 · M 渲染种子 · N 文风分布层 · O 有序列表编号 | 内容不合规约 |
| `sync_index.py` | 全库数字与 `aggregate_corpus.CANON` 一致，派生统计漂移，HTML 篇数 / 术语总条数 / 卡片张数 | 数字自相矛盾 |
| `preflight.py` | 本机路径 · 密钥 · 藏书清单 · 隐私 · 必备文件 | 发布出事 |

后两项是后来补的，起因相同：同一个数在三四处手写，每加一卷就漏改一处。

| 检查项 | 对应的实际错误 |
|---|---|
| L 桥段栏目 | 90 条里有 43 条缺了「节拍链」这一格，靠人眼数不出来 |
| L 双向覆盖 | 「双向写法」两栏只填一边，跟没填一样，本库两边的读者都要照顾 |
| HTML 篇数 | 14 卷加进来以后，README / INDEX / 12 卷 / 06-发布风险评估 这四处还写着旧数 69 |
| 术语总条数 | 写的是「311 条」，速查表实际有 315 行，差了 4 条，一直没人发现 |
| O 有序列表编号 | 一次批量重排，把红线第二节搅成 5→4→2→1→3，参考文献第 10 条跑到了最后，全库共 12 处，人眼扫不出来 |

HTML 篇数的做法是让 `build_exports` 在文件首行写一个机读标记 `<!--gb-html-docs:N-->`，
`sync_index` 就是读它来核对的。真值放进产物里，比指望人记得去改四个地方靠谱。

三个检查器都**能反复跑，会报具体位置**。报出来的每一条，都是真踩过的坑。

## 四、顺序为什么不能乱

下面这些都真出过事：脚本跑完了，一个错也没报，结果却是错的。这种错不会自己冒出来。

| 顺序 | 违反后果 | 实测 |
|---|---|---|
| `fix_mojibake` 必须在 `aggregate_corpus` 之前 | 文件名乱码还没还原就去聚合，带 GB 标记的作品被当成「非本类型」剔掉了 | 漏了 68 篇，「女攻」标签少算 1,766 次 |
| `probe_v2` 必须在 `organize_corpus` 之前 | 整理视图是一个硬链接目录，探针把它当成源文件一起扫了 | 原始文件数从 13,285 虚涨到 16,425 |
| 改完主库必须 `rebuild` | 导出产物里还是旧数字、旧内容 | HTML 里还挂着已经推翻的结论 |
| `mine` 之后必须 `rebuild` | 13 卷更新了但导出没跟上 | 同上 |
| `mine_vignette` 必须在 `render_vignette` 之前 | 渲染器读的是挖掘产出的 JSON，顺序一反，渲染出来的就是上一轮的数据 | 14 卷的频次跟 13-07 对不上 |

`run.py` 里顺序已经定死了，照着跑就行。

## 四之二、挖掘类脚本的三条方法论

这三条是挖桥段层时总结出来的，以后新加的挖掘脚本也都适用。

### 4.1 单模式命中在「结构层」必然失效

mine_text` 的八类元素都是「点」：人名、命令句、道具，单模式命中就够用。
桥段是「链」，在这一层照搬同样的做法，挖出来的全是噪声：

| 模式 | 本意 | 实际命中 |
|---|---|---|
| 「热了一次」 | 等门热菜 | 教主等下属 |
| 「等到睡着」 | 等到睡着 | 修真炉鼎戏 |

换成共现判据，结果才站得住：**同一个 2,500 字窗口里，情境族 ≥2 且反应族 ≥1**。

情境族和反应族必须分开。第一版用的是「任意 3 族共现」，命中率 99%，
组合榜前十清一色是「哭＋抱＋撒娇」，跟没测一样。反应族在哪本言情里都常见，靠它们认不出是什么场景。

### 4.2 不预设目录，让聚类反过来命名

节拍族只管「做饭／等待／哭」这样的原子动作，「等门热菜」这种桥段名不归它定。
桥段名是倒过来起的，先把共现组合聚类，再给聚出来的类命名。

先列好目录再去语料里找证据，挖到的只会是自己写下的东西。实测按预设触发词去搜，
回来的都是旁边的桥段，生病照顾＋投喂、瞒病被拆穿、临终守候，偏偏没有预设的那一个。

### 4.3 抽不动就降级成验真器，别硬抽

开放域的名词抽取做砸过两版，两次是怎么砸的，都记下来：

| 版本 | 做法 | 抽出来的是 |
|---|---|---|
| v1 | 「把／放／拿／递 + X」 | 趋向补语（放下来→「下来」） |
| v2 | 量词锚定（一碗汤、那把伞） | 词性是对了，可量词也能接抽象状态（一片空白），300 部里最后只剩下 9 个词 |
| v3 | 受控词表实测 | 可用 |

v3 让脚本退了一步，从**发现器**变成**验真器**：词表由编者给，脚本只回答「这个物件在多少部
不同作品的桥段窗口里出现过」，再算一个提升度，就是本场出现率 ÷ 一般桥段出现率。
这样一来，词表以外的物件就测不到了，好处是每个数字都能复现。

提升度算出来，特征物件才显形：生病场的体温计 1.8×，归家场的玄关 1.9×，守夜场的冰袋 3.6×。
这一步省不掉。门、车、药、手机在哪场戏里都排在前面，它们只是背景。

## 五、与模型协作的纪律

把批量重写交给子代理或外部模型时，下面这些必须写进任务说明，每一条都对应一次真出过的事故。
5.1–5.5 是早期子代理那几轮留下的，5.6 往后出自 2026-08
外部模型的八轮批量改写。

### 5.1 不许用「删标记」代替「改结构」

去 AI 化的正确做法是把散文改成表格，加粗自然下降。只删 `**` 号可以让指标达标。**什么都没改善**。

拿两个数一起看：

| 现象 | 判断 |
|---|---|
| 表格数没涨、汉字数没涨 | 一定是假的 |
| 表格数涨了、汉字数涨了 5–13% | 真的改了结构 |

实测过一份精读笔记：第一版「表 12→12、汉字 −0.1%」，打回去重做，变成「表 12→29、汉字 +6.4%」。

### 5.2 不许为指标改引文

外部引文**一字不动**，包括作品原文、社群发言、平台规则和学术文献。引文要是触发了文风指标，就在文件里注明这是例外。

优先级：**内容红线 > 分级与预警 > 去 AI 化铁律**。

两者怎么区分，见 [05-去AI化写作铁律](05-去AI化写作铁律.md)「外部引文与自引不是一回事」。

### 5.3 机械批处理必须先说清豁免

用正则批量处理，容易误伤结构性标记。踩过的有这些：

| 批处理 | 误伤了什么 |
|---|---|
| 表格单元格一律去粗 | 精读笔记信息框里的字段名，分级判定只认它 |
| 整句加粗一律去掉 | 预警标签，那是元数据 |

### 5.4 任务说明里要给可测目标与核验方法

光说「去 AI 化」不够。要写清楚当前值、目标值、拿哪个脚本测、哪些内容不许碰，还有改完怎么证明没删信息，也就是对比汉字数、比对链接、比对引文。

### 5.5 代理的报告要复核，不要照单全收

早期子代理交回的报告里，有过这些不实的说法：

- 说「已把第九个取值填入 0.2 表」，其实只写进了原型表，正表里没有
- 说「全部 30 张卡零元评论」，其实有 18 张的 `system_prompt` 和随卡世界书里还有
- 声称「安全框架完整」，实际 5 张带高风险预警的卡缺 SSC/RACK/PRICK

能测的说法都要**自己跑一遍**。检查之所以做成脚本，也是为了让复核省事，省事到每次都愿意做。

### 5.6 分工：模型改，判据判

叫模型拆掉某个括号、换掉一个行话、把一句翻译腔捋直，它干得很利索。
要它判断「这段像不像 AI 写的」，实测准头和抛硬币差不多
（数据见 [05-去AI化写作铁律](05-去AI化写作铁律.md) 第六节）。

于是分工就这么定：**具体的改交给模型，判断交给可复算的判据。**
判据得有分布、有分位数，能拿已知答案的样本来验。

### 5.7 闸门要反着写

批量作业一定要配自动闸门，哪条没过就退回原文。宁可不改，也不能改坏。
闸门有两种写法，写反了跟没设一样：

| 写法 | 效果 |
|---|---|
| 「括号不许变多」 | 模型专挑好改的改，密度只从 7.4 降到 6.1 |
| 「指定的这个括号必须消失」 | 同一批文本，密度掉到 3.8 |

想要它做到什么，闸门就直接写「必须做到」，
别写成「不许更糟」。

批量改文本时，标准闸门至少要有这几道：

- 数字：阿拉伯数字、中文数字都得查。重排时最容易把「第三拍」改成「后面那拍」，
  只查阿拉伯数字的闸门发现不了这种丢失
- markdown 链接的**地址**、竖线数、加粗数、行数、`<!--` 机读标记数
- 「」里十来个字以上的整句（引文，红线 1.3）
- 安全框架的 SSC/RACK/PRICK 字面
- 篇幅区间：缩得太狠等于删，涨得太多等于编
- 引号体例：库里一律用「」，模型喜欢换成 “”

### 5.8 三类反向验证

正面问「改好了吗」，问不出有用的东西。要反过来问，问得具体到能回答：

| 问题 | 抓什么 | 为什么反着问 |
|---|---|---|
| 新版里哪句话是旧版没有的 | 编造 | 编出来的东西具体、看得见。问「漏了什么」就得通读比对，模型干不好这个 |
| 这段里有没有指代不明的地方 | 重排打断的指代 | 「这五样东西」被挪到了「五样东西」出现之前，机械闸门全绿，可话读不通 |
| 意思变了没有 | 语义漂移 | 二选一的问法比开放式的稳 |

### 5.9 做新判据之前先校准

把两组答案已知的样本喂进去，看它能不能分开。分不开就别用。

第一版 AI 检测器把送去的 96 段**全部**判成有病。毛病出在三个评审里有一个是这么问的：
「下面这段是 AI 写的，找出最露馅的一句」，这一票永远投阳性。
什么都判阳性的检测器，什么也测不出来。

判据每收紧一格，都要回头再验一遍，看它还能不能报出真毛病。
不然走着走着，「让库通过」就悄悄顶替了「把库改好」。

### 5.10 改写换不掉骨架，重写才行，但重写不能不给原文

有一层 AI 味长在骨架上，就是先说哪件事、句子怎么起、拿什么收尾。光改词、改标点碰不到它。

试过「抽要点 → 不给原文让它重写」，实测不光没成，还危险：抽要点时整句整句地丢，
重写时凭空编（编出库里根本没有的圈内说法），篇幅涨到 2.74 倍。
**模型看不见原文，就会编。**

行得通的做法是让它看着原文改，把「换骨架」定成硬要求：开头、顺序、收尾都要换，事实一条也不许多、不许少。再配上 5.7 的闸门和 5.8 的反向验证。
另加一道**差异闸**，首句必须不一样，整体相似度要低于 0.72，不然它换几个词就交差了。

骨架已经换过的段落别再炒一遍，那就成了传话游戏。
非要跑第二轮，先「跟上一轮的备份逐段比对」，挑出没换成的，只改那些。

### 5.11 批量改写之前，先认清哪些字是机器在读的

下面这些都是接口，换一个近义词，检查器就报错，而且报错的位置跟改动的位置对不上：

三行头、分级行 `` `T` ｜ ``、`**骨架**｜`、`#### 六栏目` 的字面、
判据条的豁免标记 `<!-- gb-nonscene -->`、安全声明里的
「幻想装置／不是现实指南／SSC/RACK/PRICK」、角色卡 description 开头的「扮演方向：」声明行。

改写脚本要把这些整块跳过。出过的事：
「幻想装置」被写成「幻想道具」，C 项当场报缺声明；
「不是一场戏」被改写成「这条不算具体场景」，L 项立刻报缺栏目。
30 张角色卡里的「扮演方向：」被冲掉了，K 项一片红。

### 5.12 有序列表不是散文

「重排句序」这条指令，会把有序列表也一起重排，条目挪了位置，编号跟着条目走。
数字、链接、篇幅、markdown 都对，闸门全绿，可**列表的顺序没有哪道闸在查**。
红线第二节就变成过 5→4→2→1→3，参考文献第 10 条被甩到了第 15 条后面。
当时全库有 12 处，人眼扫不出来。

现在这一项归检查器的 **O 项**管。批量改写时，有序列表也该整段跳过。

## 六、发布

| 步骤 | 命令 / 说明 |
|---|---|
| 1. 全套检查 | `python3 _脚本/run.py publish` |
| 2. 确认入库清单 | `git status --porcelain`，核对没有 `10-藏书索引/`、`*.jsonl`、挖掘 JSON |
| 3. 提交 | 提交信息写清规模与发布边界 |
| 4. 推送 | 首次 `git remote add origin <url> && git push -u origin main` |

发布边界怎么划，完整的论证在 [06-发布风险评估](06-发布风险评估.md)。要点是**不发藏书逐条清单，只发聚合统计**。

## 七、加新素材的完整一轮

```bash
export GB_CORPUS=/path/to/your/corpus
python3 _脚本/run.py mine      # 约 50 分钟
python3 _脚本/run.py rebuild
python3 _脚本/run.py check
```

新素材很可能全是重复的。有一次「新增 4,025 篇」，MD5 一校验，100% 是已有内容的副本。现在 `check_new.py` 放在 `mine` 的第一步，后面的统计不会白跑。
